# Desktop Surface C-1 Windows native boundary verification

## Scope and immutable source

Source under test: `ab5eb3f078b63428511d758137ba7747e54396f0` (C-0).
Controller branch: `feature/dashboard-mint-ivory-v2`.
Workflow: `.github/workflows/desktop-surface-c1-native.yml`.
Required dispatch input: `expected_controller_sha`, the exact reviewed feature HEAD after committing these C-1 files. It is not the C-0 source SHA.

The workflow checks out controller and source into separate directories. The controller must descend from C-0 and its complete delta must contain only the C-1 workflow, C-1 helpers, verifier crate and this document. A guard checks repository, event, exact ref, controller/workflow SHA, immutable source, first attempt, clean checkouts and resolver lock parity before installing dependencies. Existing application source, Cargo manifest/lockfile, ACL and business behavior remain unchanged.

## Jobs and prerequisites

Two independent `windows-latest` jobs use Node 22 and stable x64 MSVC Rust, with explicit Perl/NASM/MSVC availability checks. SQLCipher uses the source's vendored OpenSSL dependency; no historical external OpenSSL override is copied. No dependency/build cache is restored. First-run duration is estimated at 45–100 minutes elapsed, 90–180 Windows runner minutes total, not a measured promise. Each job has a 120-minute bound and no automatic retry.

Production runs `npm ci`, existing Main boundary contracts, full frontend tests (`npm test -- --maxWorkers=4`), TypeScript and `npm run build`. Finance QA runs its source-stamped isolated frontend builder and TypeScript. The QA job supplies the exact QA JSON overlay through `TAURI_CONFIG` and the fixed `BOGUNON_QA_SOURCE_SHA`; enabling the feature alone is insufficient.

Both configurations run:

```powershell
cargo check --locked --manifest-path src-tauri/Cargo.toml --target x86_64-pc-windows-msvc --all-targets --message-format=json
cargo test --locked --manifest-path src-tauri/Cargo.toml --target x86_64-pc-windows-msvc --lib
```

Finance QA adds `--features my-finance-qa` to both commands. Library tests exercise existing synthetic/unit paths; no Tauri App/Window startup, probe command, native QA runner, installer or Explorer adapter is invoked.

## Generated ACL and final Context inspection

The collector identifies the source package via Cargo metadata, then requires exactly one corresponding `build-script-executed` output directory from the successful all-target check. It records the actual `acl-manifests.json` and `capabilities.json` bytes, SHA-256, source/controller/run/attempt, and source handler inventories.

The separate verifier crate uses a source-derived, Cargo-normalized lockfile. Tauri, tauri-build, tauri-codegen, tauri-macros, tauri-utils and other present Tauri components must have the same locked versions and registry checksums as C-0. The app dependency files are not edited. Verifier build.rs copies the source-generated ACL bytes into its own OUT_DIR and invokes `tauri::generate_context!` against the original source configuration path, with the same QA overlay and frontend assets. Its return type uses `MockRuntime`; no App or Window is built.

Checks include:

- Source handler counts: production 61, Finance QA 12, unique union 62.
- Generated app manifest: 124 exact allow/deny permissions and the two exact permission sets.
- Actual `get_capabilities` selection, including QA inline capability overriding file capabilities.
- Actual `Resolved::resolve` and generated Context runtime authority, not a JavaScript reconstruction of permission matching.
- Exact production/QA custom command allowlists, local Main allow and nonMain/Surface/remote deny.
- A nonMain WebView inside a Main-labelled Window is denied; window-pattern OR matching must not broaden access.
- Core/plugin commands are enumerated and receive the same static Main-only scope tests.
- Generated bytes copied into the verifier must match collected SHA-256.

`Context::runtime_authority_mut` is a **Tauri 2.11.5 version-pinned unstable diagnostic API** used only by this CI verifier. It is not introduced into production event delivery. API drift, lock mismatch, missing generated data, context-generation failure, wrong overlay or unresolved permission fails verification. This instrumentation inspects the actual generated authority without claiming end-to-end WebView IPC execution.

## Safety and evidence contract

Only `workflow_dispatch` on the exact feature ref, reviewed controller SHA and attempt 1 is admitted. Permissions are `contents: read`, both checkouts disable persisted credentials, and there is no Environment, production secret, updater signing key, release publication or installation step. Actionlint 1.7.12 is downloaded with its Windows archive SHA-256 pinned and checked before use.

Only explicitly listed diagnostic files are uploaded: Cargo check JSONL, inventory JSON, generated ACL manifests/capabilities and `ACL-REPORT.json`. Artifact names bind configuration/run/attempt. No EXE, ZIP installer, target tree or user data is uploaded. Logs use synthetic/unit inputs only; no environment/credential dump is performed. A diagnostic artifact can exist after failure or cancellation and never implies PASS. Require the complete run and both jobs to finish successfully, then compare source/controller/run/attempt and recorded hashes.

`ACL-REPORT.json` intentionally records:

- `pluginCoreGenerationRevocation: BLOCKED_NOT_IMPLEMENTED`
- `actualWindowsWebviewRuntime: NOT_VERIFIED`

Static Main label ACL does not dynamically revoke plugin/core grants on retirement. Already admitted side effects, scheduled Channel delivery and navigation TOCTOU are not solved by successful compilation or Context inspection. Actual Main/WebView2 noninterference, effective UDF, partial creation, cleanup, second-WebView isolation and Explorer attachment remain separate approval/QA work.

## Registration and execution boundary

The default branch receives only an identically named dispatch registration stub, with the same SHA input, `permissions: {}` and constant-false job. It contains no checkout, build, secret, Environment or deployment. The implementation stays on the feature branch. Existing branch protection/rules must be checked before registration; use a single-file PR and stop before merge if required.

Registration does not authorize execution. A subsequent user approval must name the final controller SHA, fixed C-0 source SHA and one dispatch. Select the feature branch, never main. On failure preserve diagnostics, classify the failed step and stop; no rerun or source repair is automatic.

## Preparation verification

Local preparation checks are Node helper syntax, executable positive/negative dispatch contracts, LF/CRLF inventory regression, existing Main boundary contracts, actionlint YAML parsing/lint, scoped rustfmt, verifier Cargo metadata with `--locked --offline`, and diff audit. Full Windows check, Rust verifier tests, generated ACL resolution and application runtime are **NOT RUN in this preparation stage**. A preparation PASS is not C-1 Windows verification PASS.

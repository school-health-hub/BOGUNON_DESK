# AUTO-UPDATE-01: Windows update foundation

## Baseline and decision

- Base source: `f3ba556eeefee565c3a5960b24b56b38254697b9` (`codex/ux-final-integration`)
- Development branch: `codex/auto-update-01`
- Existing installed beta.5, app ID `kr.sungandi.schoolhealthdesk.electronp0`, product name `BOGUNON DESK`, profile `BOGUNON-DESK-ELECTRON-P0`: unchanged
- Electron `45.2.1`, electron-builder `26.18.0`; NSIS is per-user (`perMachine:false`, `allowElevation:false`), AppData is retained on uninstall. Portable is separate. Current `publish:null` produces no update feed.
- Chosen distribution direction: a project-controlled HTTPS generic feed with a pinned Ed25519 public key in the app, signed JSON manifest, same-origin NSIS URL, declared size, and SHA-256. The private key stays outside Git and the application. A private beta feed needs an operator-controlled access service; the application must never carry a GitHub developer token.

The code implements update discovery, explicit download consent, progress, cancellation, SHA validation, and a Korean status panel in Settings > App information. `config/production-electron-update.json` is deliberately disabled, so this development build does not contact a production update server. Automatic installation is deliberately unavailable: the existing Windows installer is unsigned and there is no approved Authenticode publisher. No code-signature verification was disabled. `electron-updater` was **not** added or claimed to be operational. After signing and server approval, integrate the official NSIS updater with a matching publisher identity and a separate install-consent/unsaved-work gate, or implement an equivalent signed-installer handoff and test it in an isolated Windows installation.

The repository's Tauri updater scripts are unrelated to this Electron implementation. Builder's `publish:null` remains unchanged; `latest.yml` is not generated by this candidate. `sign-update-manifest.mjs` creates the separate signed JSON feed only after a matching signing key, configured public key, version-matched NSIS, and HTTPS origin exist.

## Provider comparison

| Option | Operating cost and work | Private beta | School network / public scale |
| --- | --- | --- | --- |
| Public GitHub Releases | Low server work; release asset and bandwidth terms apply | Public artifacts do not meet a restricted pilot; private assets require client credentials | GitHub may be blocked; suitable for later public releases |
| HTTPS generic server (chosen) | Storage, bandwidth, TLS and access gateway cost; operator must upload atomically | Can enforce access at the server without embedding a developer token | Requires a school-network reachability check; can later serve public releases |
| Google Drive share link | Existing storage, but redirect/content and stable metadata behavior are unsuitable as a trusted updater feed | Manual sharing only | Retained for manual transfer, not automatic update |

The chosen server and credentials have **not** been provisioned. A restricted pilot additionally needs a backend-issued access mechanism or a separate manual installation bridge; public access must not be silently enabled.

## State and data contract

- Main owns network, signature verification, hash verification, and the update cache. Renderer receives only a bounded status object over fixed IPC; it cannot supply a URL, path, or key.
- `idle → checking → current / available / failed`; `available → downloading → ready / available (cancelled) / failed`. A same-version result does not download. A lower version is rejected.
- Redirects are refused. Feed and EXE must be HTTPS on the same origin. Metadata is capped at 64 KiB, the EXE at 1 GiB, and partial files are removed on failure.
- The updater does not migrate, delete, or rewrite the existing settings, memo, authentication, Dock, Palette, or work-data stores. Only `update-downloads` under the app profile would be written after a user accepts a valid signed download.
- The current beta.5 has no update UI; its first move to an update-capable build must be a **separately approved manual NSIS install**, with a complete profile backup and restore candidate. Preserve app ID, profile name, and per-user install identity.
- Portable returns an unavailable status. It never invokes the NSIS update path.

## Activation conditions

1. Approve an HTTPS endpoint and private-beta access design. Confirm reachability from a permitted school test network.
2. Establish an Ed25519 signing key kept in approved secret storage and put only its public key and feed URL in the next build. Generate the JSON manifest from the exact NSIS bytes and upload EXE first, manifest last.
3. Obtain and configure a Windows code-signing certificate; retain signature verification and pin the expected publisher for NSIS installation. Validate the selected `electron-updater` version against Builder 26 before adding it. Do not silently update to Builder 27.
4. Build a versioned, update-capable NSIS candidate and manually bridge beta.5 users once, with backups. Verify installed and portable detection separately.
5. In an isolated Windows installation, test signed download, install consent, unsaved-work guard, restart, installed version, profile hashes, interrupted update, and retry. Only then enable in-app installation or publish the feed.

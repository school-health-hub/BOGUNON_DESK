# 학교·집 PC용 MY FINANCE QA 설치·백업·복원·제거 안내

이 문서는 **전용 QA 설치 파일**에만 적용합니다. 운영 BOGUNON DESK는 제거·초기화·업데이트하지 않습니다. 실제 금융정보·학생/학교 업무자료·운영 로그인 계정을 사용하지 않습니다.

## 1. 받을 파일과 실행 전 확인

GitHub 저장소 → **Actions → MY FINANCE isolated Windows QA → 해당 검증 커밋의 성공한 실행 → Artifacts**에서 `MY-FINANCE-QA-TESTABLE-<전체커밋>` ZIP을 받습니다. 실패한 실행이나 `ISOLATION-EVIDENCE`는 설치용이 아닙니다. 일반 `windows-clean-install-qa-*`의 운영 ID 설치 파일은 이 테스트에 사용하지 않습니다.

압축을 새 폴더에 풀면 다음이 있습니다.

- `BOGUNON-DESK-MY-FINANCE-QA-<7자리커밋>-Windows-x64-Setup.exe`
- `SHA256SUMS.txt`: 설치 파일 해시
- `QA-TEST-STATUS.json`: `testable: true`, `status: passed`, 원본 커밋, 실제 Authenticode 서명 상태, 격리 검증 결과
- `START-HERE.ko.md`: 이 안내

`QA-TEST-STATUS.json`에서 `sourceSha`와 성공한 Actions 커밋이 같은지 확인합니다. **TESTABLE은 합성 자료를 이용한 테스트 가능 표시이며 실사용 준비 완료나 코드서명 완료라는 뜻이 아닙니다.** 자동 검증은 한 일회용 Windows 러너 안에서 수행합니다. 실제 학교·집 PC의 권한·장치 정책·서로 다른 Windows 계정·정전/키 손실 복구는 미검증입니다.

파일 해시 확인은 읽기 전용입니다. 압축 푼 폴더에서 우클릭 → **터미널에서 열기** 후 다음을 붙여넣습니다. 설치 파일이 한 개만 있는 폴더에서 실행합니다.

```powershell
Get-ChildItem .\BOGUNON-DESK-MY-FINANCE-QA-*-Windows-x64-Setup.exe | Get-FileHash -Algorithm SHA256
Get-ChildItem .\BOGUNON-DESK-MY-FINANCE-QA-*-Windows-x64-Setup.exe | Get-AuthenticodeSignature | Select-Object Status,Path
```

해시는 `SHA256SUMS.txt` 및 결과 댓글/Actions의 `MY_FINANCE_QA_SHA256` 값과 같아야 합니다. 서명 상태도 결과와 같아야 합니다. `NotSigned`라면 Microsoft가 게시자를 인증한 파일이 아닙니다. 기관 정책상 실행 가능한지 먼저 확인하며, 보안 기능을 끄거나 SmartScreen을 강제로 우회하지 않습니다. 해시 불일치·예상 밖 서명·보안 차단·관리자 설치 요구가 나오면 취소합니다.

## 3. 학교 PC 설치와 학교 백업 만들기

1. Windows **설정 → 앱 → 설치된 앱**에서 기존 BOGUNON DESK의 표시 버전·기존 바로가기 대상·기존 데이터 폴더 존재 여부만 기록합니다. 제거/수정/초기화를 누르지 않습니다. 학교 PC 정책상 설치가 허용되지 않으면 진행하지 않습니다.
2. 검증한 QA 전용 EXE를 엽니다. 설치 화면 이름이 **BOGUNON DESK MY FINANCE QA**인지 확인합니다. 운영 앱 업데이트/제거/복구 화면이나 운영 설치 위치가 나오면 **취소**합니다. QA 경로가 맞을 때만 **설치 → 완료**를 누릅니다.
3. 시작 메뉴에서 **BOGUNON DESK MY FINANCE QA**를 엽니다. 노란 QA 띠와 경로를 확인합니다. 기존 업무/로그인/금융정보가 보이면 즉시 중단합니다. QA 앱에서 운영 계정 로그인을 시도하지 않습니다.
4. **수입 등록**으로 아래 합성 자료를 한 건씩 넣습니다. 세무 분류는 **미확인**, 증빙 확정은 체크하지 않습니다. 계약 명목/메모에는 `합성 테스트`를 씁니다. 금액은 쉼표 없이 입력합니다. 공제는 **공제 추가 → 소득세**를 선택합니다. 매번 **등록 내용 확인 → 로컬 저장**을 누릅니다.

| --- | --- | --- | --- | --- | --- |
| 합성 학교 급여 | 학교 급여 | 2026-03-10 | 2026-03-25 | 1000000 | 33000 |
| 합성 강의 | 강의 | 2026-03-10 | 비움 | 200000 | 6000 |

5. 연도 **2026**, 유형 **전체 수입**을 선택합니다. 총수입 **1,200,000원**, 공제 **39,000원**, 실수령 **1,161,000원**, 미입금 **1건**을 확인합니다. 2025년 자료는 2026년 합계에서 제외됩니다.
6. **백업·복원 → 백업 내보내기 → 백업 비밀번호·비밀번호 확인 → 암호화 파일 저장**. 합성 자료 전용 비밀번호를 정하고 새 이름 `SYNTHETIC-SCHOOL-01.bgfnbk`로 저장합니다. 비밀번호는 파일과 분리해 보관합니다. 기존 백업은 덮어쓰지 않습니다.
7. 기관 정책에 맞게 **암호화 백업 파일만** 집으로 이동합니다. 운영/QA DB·`key.dpapi`·로그인·업무 파일은 옮기지 않습니다. 계정 동기화를 사용하지 않습니다.

## 4. 집 PC 설치와 최초 이식

1. 집 PC에도 학교와 **같은 검증 커밋·해시의 QA 설치 파일**을 사용합니다. 위 설치 전 확인을 반복하고 QA 이름/설치 경로를 확인하여 설치합니다. 운영 앱은 유지합니다.
2. 집 QA 앱은 아직 수입을 한 번도 작성하지 않은 빈 저장소여야 합니다. 시험 삼아 수입을 등록하고 지웠다면 최초 이식 자격이 없어집니다. 그 경우 삭제/초기화로 우회하지 말고 중지합니다.
3. **백업·복원 → 백업 복원 → 백업 파일 선택**으로 학교 파일을 고릅니다. 잘못된 테스트 비밀번호로 **복호화 및 유효성 검사**를 눌러 오류 후 데이터가 그대로인지 확인한 다음, 올바른 비밀번호로 검사합니다.
4. **최초 PC 이식 · 데이터셋 변경**의 현재/백업 ID를 확인합니다. 동의 전에는 최종 확인 버튼이 비활성화되어야 합니다. **빈 저장소의 데이터셋 변경에 동의합니다 → 복원 최종 확인**을 누릅니다.
5. 한 번 **취소**하여 데이터가 바뀌지 않는지 확인합니다. 다시 확인창을 열고 실제로 진행할 때만 **데이터셋 변경 후 이식**을 누릅니다. 5분이 지났거나 상태가 변경되었다면 파일 선택부터 재검사합니다. 자동 재시도/덮어쓰기는 하지 않습니다.
6. 학교와 같은 내역/2026년 합계를 확인합니다. QA 창을 완전히 닫았다가 다시 열어도 같아야 합니다. 수정 없이 집에서 새 파일로 내보내 학교에서 검사하면 **현재 데이터와 같습니다**가 기대 결과입니다. 암호화 파일은 랜덤 salt/nonce 때문에 바이트가 같을 필요는 없습니다.

## 5. 집 수정 → 학교 복원

1. 집 QA 앱의 합성 강의 **수정**: 총수입 `250000`, 소득세 `7500`, 입금일 `2026-04-01` → **수정 내용 확인 → 로컬 저장**.
2. **수입 등록**: 합성 자문 / 자문 / 2026-03-10 / 입금일 비움 / 총수입 `100000` / 공제 없음 / 세무 미확인 → 확인·저장.
3. 새 암호화 파일 `SYNTHETIC-HOME-02.bgfnbk`로 내보내 학교로 옮깁니다.
4. 학교 QA 앱의 백업 복원에서 파일·비밀번호를 검사합니다. 같은 데이터셋의 후속 백업 안내를 확인하고 **복원 최종 확인 → 안전 스냅샷 후 복원**을 누릅니다.
5. 학교·집에서 2026년/전체 수입 **총수입 1,350,000원 / 공제 40,500원 / 실수령 1,309,500원 / 미입금 1건 / 3건**을 확인합니다. 2025년 전자책도 해당 연도에 남아 있어야 합니다. 학교 QA 앱도 종료·재실행하여 확인합니다.
6. 학교에서 새 백업을 만들어 집에서 검사하면 같은 데이터 판정이어야 합니다. 자동 테스트는 전체 datasetId/revision/history/수입 동일성을 비교합니다. DB를 직접 열어 확인할 필요는 없습니다.

## 6. 마지막에 충돌 차단 확인

먼저 정상 왕복을 마친 후 진행합니다. 학교에서 합성 급여 메모를 `합성 학교 수정`, 집에서 합성 강의 메모를 `합성 집 수정`으로 각각 저장합니다. 새 백업을 서로 검사하면 **변경 이력 충돌**로 차단되어야 합니다. 다른 항목을 수정했더라도 자동 병합하지 않습니다. 오래된 `SYNTHETIC-SCHOOL-01.bgfnbk`도 차단되어야 합니다. 다른 데이터셋/손상 파일은 별도로 준비된 합성 시험 파일이 있을 때만 검사하고, 없으면 미실행으로 기록합니다. DB/키를 삭제하거나 직접 변조하지 않습니다.

## 7. 학교 PC와 집 PC에서 QA 앱만 제거하기

각 PC에서 따로 진행합니다. 테스트 종료 후 제거를 원할 때만 사용합니다.

1. 필요한 **합성** 백업이 있다면 먼저 새 암호화 파일로 보관합니다. QA 앱의 X 또는 **QA 앱 종료**로 닫습니다. 운영 앱은 제거/종료할 필요가 없습니다.
2. Windows **설정 → 앱 → 설치된 앱 → BOGUNON DESK MY FINANCE QA → ⋯ → 제거**. 이름에 **MY FINANCE QA**가 없는 운영 BOGUNON DESK에는 손대지 않습니다.
3. 제거 화면에서 **Delete app data / 앱 데이터 삭제** 항목이 보이면 반드시 체크하지 않습니다. 이번 QA는 금융 DB·키를 제거 후에도 보존하는 조건입니다. 운영 폴더 또는 QA 데이터 폴더를 수동 삭제하지 않습니다.
4. QA 바로가기가 없어지고 운영 앱·바로가기·기존 설정이 남아 있는지 확인합니다. QA Local 경로의 `my-finance\finance.db`, `key.dpapi`는 남는 것이 정상입니다. 같은 QA ID로 재설치하면 합성 자료가 다시 보이며, 다시 빈 PC로 취급되지 않습니다.
5. 운영 앱/데이터가 바뀌거나 없어진 것 같으면 아무 것도 초기화하거나 재설치하지 말고 중지합니다. 보고에는 PC 구분·QA 커밋·해시·실행한 단계·오류 문구만 적고 DB/키/로그인 파일·실제 업무/금융 내용을 첨부하지 않습니다.

아직 수동으로 확인하지 않은 범위는 물리적으로 다른 두 PC의 왕복 복원, 복원 후 새 변경을 원래 PC로 되돌리는 후속 revision 복원, 양쪽 동시 변경 충돌, 실제 정전·저장장치 손실·계정 손실 복구입니다. 자동화 테스트가 이 범위를 일부 검증하더라도 실제 장치 수동 검증과 동일하게 기록하지 않습니다.

## 자동 격리 검증의 범위와 한계

새 워크플로는 일회용 GitHub-hosted Windows에서만 실행되도록 차단합니다. 운영 기준 소스는 고정된 main `5cec64358436c148710499b5aa9d2e78c34e0136`이며 운영 업데이트/배포는 하지 않습니다. 테스트 중 두 앱 및 WebView의 외부 연결을 CI 방화벽으로 막습니다. 실제 사용자의 PC나 데이터를 이용하지 않습니다.

운영 기준 앱을 먼저 설치·실행하고, 유효한 합성 SQLCipher/DPAPI 금융 DB·업무 표식을 만든 뒤 비교합니다. 운영 앱이 닫힌 구간에서는 전체 설치/Local/Roaming 파일 및 등록 정보 해시를 QA 설치·실행·제거 전후 비교합니다. 동시 실행 구간에서는 운영 앱 자체가 WebView 캐시를 갱신할 수 있으므로 설치 파일·금융 DB/키·보존 표식·OS 등록 정보의 동일성과 운영 프로세스 생존을 비교합니다. QA 앱만 두 번 제거하며 운영 앱은 제거하지 않습니다. QA 금융 DB/키도 제거 전후 보존되어야 합니다.

설치된 QA WebView에서 실제 네이티브 CRUD·저장 위치·연간 집계·재설치 후 지속성을 확인하고, 업데이터/로그인/자동 시작/딥링크 명령이 등록되지 않았는지 검사합니다. 별도 Rust 합성 테스트는 백업·최초 이식·왕복·분기 차단·중단 복구를 검증합니다. CDP 디버깅 포트는 CI 프로세스 환경에서만 지정하며 설치 파일에 포함하지 않습니다.

모든 검증을 통과한 뒤에만 테스트했던 정확한 설치 바이트를 `TESTABLE` 패키지에 복사합니다. 이 검증이 실제 학교·집 PC의 모든 과거 운영 버전/계정/보안 정책에서 무조건 안전함을 보장하지는 않습니다. QA-39C에서 같은 Windows 11 Pro PC의 별도 표준 사용자 간 최초 이식과 재실행 영속성은 수동 검증했지만, 실제 두 물리 PC의 왕복 QA와 장애 복구 검토 전에는 실사용 준비 완료로 표시하지 않습니다.

# MY FINANCE 암호화 백업·안전 복원

개발 검증용 기능입니다. 실제 금융정보를 사용하지 않습니다. 학교·집의 실제 두 PC 간 검증 및 장애 복구 절차 검증을 마치기 전에는 실사용 준비 완료로 표시하지 않습니다.

## 사용자 흐름

- MY FINANCE → 백업·복원 → 백업 내보내기: 비밀번호와 확인란을 입력한 뒤 네이티브 저장 대화상자에서 **새 파일명**을 선택합니다. 기존 파일은 덮어쓰지 않습니다. 비밀번호 분실 시 복구할 수 없습니다.
- 백업 복원: 네이티브 파일 선택 → 비밀번호 입력 → 복호화·검증 결과 → 별도 최종 확인. 검사는 파일 선택 후 5분 동안 유효합니다. 취소·닫기는 복원하지 않습니다.
- 사용 이력이 없는 빈 저장소는 **수입 0건 + revision 1 + history 1개인 유효한 초기 스냅샷**일 때만 다른 데이터셋의 최초 이식을 허용합니다. 변경 전/후 datasetId를 안내하고, 데이터셋 변경 동의 체크와 별도의 최종 확인을 받습니다. Rust도 데이터셋 변경 확인 인자를 요구합니다.
- 사용한 저장소는 같은 데이터셋의 현재 이력을 포함하는 **후속 revision**만 허용합니다. 수입을 모두 삭제했어도 변경 이력이 있으면 최초 이식을 허용하지 않습니다. 오래된 백업, 같은 데이터, 다른 데이터셋, 이력 분기, 동일 identity의 다른 내용, 미지원 버전 및 잘못된 금액은 차단합니다.
- 검사 이후 현재 데이터가 변경되면 복원을 차단합니다. 실패·응답 불확실 시 새로고침으로 현재 상태를 확인하고 파일부터 다시 선택해야 합니다. 자동 재시도·자동 덮어쓰기는 없습니다.

## 보존 및 원자성

`finance.db`와 `key.dpapi` 구조를 유지합니다. 복원 시 DPAPI 키를 교체하지 않습니다.

1. SQLCipher `BEGIN IMMEDIATE`로 전체 현재 스냅샷과 검사 당시 스냅샷을 비교하고 복원 정책을 다시 검증합니다.
2. 현재 스냅샷을 같은 암호화 DB의 `finance_restore_safety` 테이블에 별도 UUID로 삽입하고 먼저 커밋합니다. 안전 스냅샷 저장 실패 시 실제 데이터 교체를 시작하지 않습니다. 이 테이블은 추가형 내부 구조이며 기존 DB 및 휴대용 스냅샷 버전은 변경하지 않습니다.
3. 두 번째 `BEGIN IMMEDIATE`에서 전체 현재 데이터를 다시 비교합니다. 첫 커밋 이후 다른 프로세스가 변경했어도 덮어쓰지 않습니다.
4. 현재 payload를 검증한 백업 payload로 교체하고 커밋합니다. 교체·커밋 오류와 커밋 이전 프로세스 강제 종료는 SQLite 롤백 저널로 기존 데이터를 유지합니다. 안전 스냅샷은 이미 커밋되어 남습니다.

복원은 수입 데이터와 identity/history 전체를 한 트랜잭션으로 교체합니다. 백업의 revision/history를 그대로 채택해 불필요한 이력 분기를 만들지 않습니다. 안전 스냅샷은 자동 삭제하지 않으며 외부로 내보내지 않습니다. 같은 DB 안의 안전 스냅샷은 DB 파일 손실이나 DPAPI 키 손실에 대비한 외부 백업을 대체하지 않습니다. 내부 안전 스냅샷 선택·되돌리기 UI는 이번 기능에 포함하지 않습니다.

## 파일 형식과 경계

기존 `BGFNBK01` 형식을 유지합니다: 8바이트 magic + 16바이트 랜덤 salt + 12바이트 랜덤 nonce + AES-256-GCM ciphertext/tag. 전체 헤더를 AAD로 인증합니다. Argon2id v0x13, 64 MiB, 3 iterations, parallelism 1, 256비트 파생 키. payload는 기존 schema 2 JSON 스냅샷입니다. PC 종속 키·경로·계정·DPAPI 값은 파일에 포함하지 않습니다.

파일의 암호화 및 복호화는 PC 키와 독립적입니다. 최초 이식 후 수입 전체와 datasetId/revision/history를 원본 그대로 채택합니다. 새 PC의 자체 SQLCipher/DPAPI 키는 변경하지 않습니다. 따라서 각 PC의 키를 옮길 필요가 없습니다. 학교→집 최초 이식 후 집에서 변경한 후속 백업은 학교로 복원할 수 있습니다. 두 PC가 각자 변경하여 이력이 분기되면 더 높은 revision이어도 차단하며 자동 병합하지 않습니다.

초기 상태 판정은 UI의 빈 목록을 신뢰하지 않고 트랜잭션 안에서 검증한 전체 스냅샷으로 결정합니다. 임의의 초기화/재설정 명령은 추가하지 않습니다. 빈 초기 백업(revision 1)을 이식한 저장소는 여전히 사용자 변경 이력이 없으므로 같은 초기 상태 기준을 적용합니다. 수입을 생성/수정/삭제한 저장소는 영구적으로 revision이 증가하여 이식 대상이 되지 않습니다.

파일 경로는 Rust 네이티브 대화상자에서만 받습니다. 렌더러는 임의 경로를 명령에 전달하지 않습니다. 최대 약 64 MiB로 파일 읽기를 제한하고, 선택한 암호문을 세션에 고정하므로 검사 이후 파일 변경은 복원 내용을 바꾸지 못합니다. 검사를 통과한 payload와 현재 pre-image는 Rust 메모리에 zeroizing 직렬화 버퍼로 보관합니다. 복원 티켓은 일회용이며, 실패 시에도 소비합니다. 비밀번호는 화면에서 호출 즉시 지우며 Rust에서 Zeroizing으로 감쌉니다. JavaScript 문자열·런타임 복사본의 완전한 메모리 삭제를 보장하는 기능은 아닙니다.

금융 데이터·비밀번호·키를 브라우저 저장소, 로그, 이벤트, 원격 분석, 계정 또는 서버에 보내는 경로는 추가하지 않습니다. UI 오류는 고정 문구만 표시합니다. 파일 저장 임시 파일에도 암호문만 씁니다. 잘못된 비밀번호와 변조는 모두 인증 실패로 거부합니다.

## 검증

모든 테스트는 합성 데이터만 사용합니다. Windows Actions에서 실제 앱의 Rust 모듈, SQLCipher, DPAPI 재실행 테스트를 실행합니다. 강제 종료 테스트는 별도 테스트 프로세스를 교체 트랜잭션 도중 exit(73), 최초 이식은 exit(74)로 종료한 뒤 원래 스냅샷 및 안전 스냅샷을 확인합니다. 성공 후 별도 프로세스로 다시 열어 데이터도 검증합니다. 오류 주입으로 안전 스냅샷 저장 실패, 교체 실패, 커밋 실패도 검사합니다. UI 테스트는 비밀번호 오류, 검사와 최종 확인의 분리, 차단 정책, 중복 클릭, 비밀번호 지우기, 네트워크/브라우저 저장 미사용을 검사합니다.

Windows 앱 빌드·설치·재실행·제거 QA와 Chromium UI 검증은 각각 플랫폼 통합과 화면 동작을 확인하는 범위입니다. Chromium의 합성 IPC 대역은 Windows 네이티브 파일 대화상자 수동 QA를 대체하지 않습니다. 실제 학교·집 PC 이동이나 실제 금융자료 검증을 수행했다고 해석하지 않습니다.


## 교차 PC 자동 검증 범위

`src/my-finance/fixtures/cross-pc-synthetic.json`을 Rust/JavaScript 테스트가 함께 사용합니다. 학교에 합성 수입 3건을 작성하고 암호화 파일을 내보낸 뒤, 독립 키를 가진 빈 집 DB에 이식합니다. 집에서 강의 수입을 수정하고 자문 수입을 추가하여 다시 내보내고 학교에 복원합니다. 각 단계에서 DB를 다시 열어 수입 및 datasetId/revision/history 전체의 동일성을 확인합니다. 최종 revision 6의 연간 집계는 2026년 3건, 총수입 1,350,000원, 공제 40,500원, 실수령 1,309,500원, 미입금 1건이며 2025년 수입은 제외됩니다. 같은 합성 수입을 실제 UI에 복원한 후 화면 재실행 때도 같은 집계를 확인합니다.

Windows 테스트는 별도 설치 디렉터리 두 개의 독립된 DPAPI 보호 키로 동일한 왕복 시나리오를 실행합니다. 양쪽 DPAPI 키 파일이 유지되고 다른 키로 DB를 열 수 없음을 확인하며, 별도 프로세스에서 두 DB를 다시 열어 전체 스냅샷과 기대 수입을 비교합니다. 이는 **한 Windows 러너/사용자 안의 두 저장소** 검증입니다. 서로 다른 물리 PC/Windows 계정의 DPAPI·파일 대화상자·실제 장치 이동 검증은 아닙니다.

## 실제 학교·집 PC 수동 QA — 미실행

실사용 준비 완료로 판단하기 전에 다음을 합성 데이터와 분리된 테스트 환경에서 확인해야 합니다. 기존 사용 DB를 삭제하거나 revision/history를 초기화해 최초 이식 제한을 우회하지 않습니다.

- [ ] 같은 검증 커밋의 Windows 설치 파일을 실제 학교·집 PC의 테스트 환경에 설치·실행한다. 앱 업데이트/재설치 후 기존 DB와 DPAPI 키가 유지되는지 확인한다.
- [ ] 학교에서 위 합성 자료를 입력하고 네이티브 저장 대화상자로 새 `.bgfnbk` 파일을 만든다. 비밀번호는 파일과 분리해 보관한다. 파일만 이동하며 DB/DPAPI 키는 복사하지 않는다.
- [ ] 사용자 수입/변경 이력이 없는 집 PC에서 파일을 선택한다. 잘못된 비밀번호는 거절되고, 올바른 비밀번호로 검사하면 현재/백업 datasetId와 최초 이식 동의가 표시되는지 확인한다. 동의나 최종 확인을 취소하면 데이터가 바뀌지 않아야 한다.
- [ ] 명시적으로 최초 이식을 확인한 후 수입·연도별 집계를 확인하고 앱을 완전히 종료·재실행한다. 집에서 그대로 재백업하여 학교에서 검사했을 때 “현재 데이터와 같습니다”로 판정되는지도 확인한다. 이 판정은 Rust의 전체 identity/history/수입 비교에 따른다.
- [ ] 집에서 합성 수입을 수정/추가한 후 학교에 후속 복원하고 기대 집계를 확인한다. 학교에서 다시 백업해 집에서 검사하여 같은 데이터 판정을 확인한다.
- [ ] 양쪽에서 각각 합성 메모를 수정하고 상대 백업을 검사하면 이력 충돌로 거절되는지 확인한다. 기존 다른 데이터셋이 있는 저장소, 등록 후 모두 삭제한 저장소, 오래된 파일, 손상된 파일도 거절되어야 한다.
- [ ] 실제 네이티브 파일 대화상자의 취소·접근 불가·기존 파일명 충돌, 학교 장치 정책과 이동식 저장장치에서의 읽기/쓰기 동작을 확인한다.
- [ ] 별도 장애 QA 환경에서 OS/프로세스 종료·재시작 후 원본 또는 완전히 복원된 데이터만 존재하는지 확인한다. 자동 exit 주입 테스트가 실제 정전·저장장치 손실·DPAPI 계정 손실 복구를 입증하지는 않는다.

이 체크리스트는 실행 결과가 아니라 남은 수동 검증 항목입니다. 실제 금융정보를 테스트에 사용하지 않으며, main 병합·배포나 실사용 준비 완료를 선언하지 않습니다.

## Native callbacks that bypass custom-command wrappers by design

`lib.rs::create_tray` calls `execute_registered_action` directly for hard-coded menu IDs; `show_main_window` and tray icon left click show/focus Main, and quit sets `DesktopState.quitting` then exits. Single-instance callback shows Main. Setup installs the Main guard, creates tray, and calls `launcher::schedule_work_portal_auto_open`; the delayed task reads launcher configuration and opens the portal via the internal helper. These are trusted native entry points, not arbitrary webview requests. Keep their shared internal helpers callable without constructing a fake Webview or weakening the invoke wrapper. A new menu ID/remote action dispatcher requires its own bounded action allowlist review.

`lib.rs::on_window_event` is also native, but its **window role is not restricted**: Drop obtains global `PurchaseHelperState` and, if active, begins analysis, reads dropped files in a background task and broadcasts results via that Window receiver. If inactive it broadcasts full paths. A Window receiver does not narrow `Emitter::emit` delivery in locked Tauri 2.11.5. This is the concrete residual route around command wrappers for file work. Gate to pinned Main before analysis-generation changes, state-derived templates, file access or payload construction if other windows are introduced. Native OS provenance does not authorize every window role.

The same callback handles CloseRequested for every window using application-wide close-to-tray/quitting flags and can prevent close/hide a future Surface. It needs explicit per-role close/lifecycle policy before multi-window production use. This audit makes no production lifecycle change.

## Existing stale-result protections and their limits

`PurchaseHelperState` owns active, AtomicU64 generation and template mutex. `set_purchase_helper_active` invalidates the generation; `invalidate_purchase_helper_analysis` increments it; `complete_analysis` drops results unless active and current. `purchaseHelperNativeLifecycle.ts` queues active/template state calls, disposes late registrations, checks mounted before callbacks, and clears active on disposal. `PurchaseHelperPanel.tsx` disables result acceptance while closing/resetting and uses exact generation equality for result/error application. These are useful protections and should be retained.

They do not identify the registered Main lifetime: generation is process-local analysis sequencing and has no window/Webview identity, account/workspace revision or recipient epoch. State checking and emitting are separate operations; generation invalidation can happen between them. An already emitted event can arrive after ownership changes. A start event can overwrite latest generation without checking monotonicity. Native Rust u64 is represented as JS number in the current DTO, so it is not an unlimited exact identifier across that boundary. A future contract should use an opaque operation ID or safe serialized integer and enforce current recipient + revision at receive time. This is a design requirement, not a claim of a reproduced exploit.

## Required future event contract (no Surface grant in this change)

1. Backend pins destination identity and instance epoch. A label is only a role hint; revoked/destroyed/replaced Main or Surface must not inherit a previous recipient registration.
2. Each async operation records the authorized originating instance, operation ID, data/workspace/account revision and generation. Revalidate ownership before delivery; receiver rejects wrong instance, old revision, replay/out-of-order generation and unknown schema.
3. Use targeted delivery to an authorized current recipient. Event name, payload TS type, generation equality, and listener registration are not secrets or origin authentication. Capability permissions must independently prevent unauthorized JS emit/listen/emit-to usage.
4. Separate confidential Main result DTOs from any independently reviewed minimal future Surface display DTO. No tokens/session values, callback URLs, account/portal URLs, absolute paths, extracted text, raw purchase candidates or process/shell diagnostics in Surface events.
5. On dispose, account/workspace switch, replacement, or revocation, invalidate operations and recipient registration; queued callbacks must be harmless. Specify cancellation result and request/response correlation so cancelled pickers do not leave busy UI indefinitely.
6. Add synthetic tests for wrong recipient, stale instance/generation/revision, reordered start/result, post-disposal events, emit-after-invalidation, and Surface drop/close rejection. No test should need real credentials, school files, browser or Explorer mutation.

## Capability context and conclusion

`src-tauri/capabilities/default.json` scopes capabilities to `windows: ["main"]` and includes `core:event:default`, deep-link, notification and updater permissions. `tauri.conf.json` currently declares one application window, with restrictive CSP; test-only lifecycle simulation is not a production Surface registration. This reduces current exposure but does not establish a universal guarantee about future windows or custom command identity. Exact per-webview plugin capability policy and event destination identity are independent of the 48 custom wrappers. Do not add Surface capability scope, event subscriptions, a Surface allow enum, a projection endpoint, window creation or attach logic as part of this hardening.

Static audit result: wrapping all 48 custom commands closes their invoke admission boundary. App-wide sensitive events and role-agnostic native window handlers remain explicit follow-up constraints before any additional production webview. No existing event has a complete instance + generation + revision envelope. Current purchase events have generation only; navigation/notice/drop have none.

# 운영자가 결정할 정책

아래는 권고 초안이며 이번 로컬 테스트 통과가 실제 재직 확인·정책 승인을 대신하지 않는다.

## 최초 학교 관리자

1. 교육청코드+NEIS 학교코드(text, 선행0 보존)를 서버의 신뢰 directory와 대조한다. 학교명/개인 프로필/이메일 도메인만으로 인정하지 않는다.
2. 신청자는 Auth 계정으로 학교 공간 개설 요청을 제출한다. 상태 pending, 관리자/학교 공유 접근권한 없음.
3. 운영 책임자가 정한 담당자 A가 보건교사 재직 또는 적법한 위임, 요청 학교, 신청 계정의 통제권, 관리자 책임 동의를 외부 절차로 확인한다.
4. 독립 담당자 B가 증거 참조와 동의를 재확인해 승인한다. 본인 신청·동일 담당자 셀프 승인 금지.
5. 서버는 신뢰 directory·현재 unclaimed·기존 관리자 없음·요청자 active·대상 상태·검증 유효기간·동의 참조·버전을 재검증한 뒤 학교 활성/첫 관리자/감사를 한 transaction으로 기록한다.
6. 추가 관리자는 기존 propose→accept 절차로 보건교사만 승격한다. 지원강사 즉시 관리자 승격 금지. 최소1명·복수 관리자 허용.
7. 마지막 관리자 탈퇴/강등/정지는 서버가 막는다. 분실/휴직/퇴직으로 관리자가 불능인 학교는 recovery_locked와 별도 증빙 재검증·독립 승인·감사 후 복구한다.
8. recovery_locked 학교에 최초개설 bootstrap을 재사용하지 않는다. 인수인계 완료 전 기존 계정 데이터 삭제로 해결하지 않는다.

실험 SQL은 **운영자 검증 결과를 소비하는 control plane**이다. 보건교사 재직을 DB가 자동 판정하지 않는다.
외부 증빙 원문/연락처/인증번호를 저장하지 않고 무작위 case/consent UUID와 증빙 SHA-256만 기록한다.
해시도 연결 가능한 개인정보일 수 있으므로 공개하지 않고 보존·폐기 정책을 적용한다.

`ws_bootstrap_operator`는 DB 운영 principal allowlist+role membership으로만 부여된다.
Google 로그인 role/학교 관리자 role과 별개며 authenticated·학교 관리자·BFF 일반 요청에는 부여하지 않는다.
`ws_bootstrap_executor`는 비소유 NOBYPASS 실행 역할이며 운영자는 그 역할을 직접 SET할 수 없다.
감사에는 실제 operator principal+연결 계정 actor를 기록하고 신청자 계정으로 대행한 것처럼 남기지 않는다.
실행권한도 기본 CLOSED, 테스트에서만 명시 활성화한다. 운영용 관리자 콘솔/연결/실제 권한 부여는 구현하지 않았다.

퇴직자 개인 계정을 학교 다른 사람에게 양도하지 않는다. 학교 소속만 종료하고 학교 기록은 보존한다.
계정 비활성화·Membership 종료 후 새 요청은 차단한다. 보존기간 미정 상태를 영구 보존 승인으로 해석하지 않는다.

현재 서버 계약의 구체 제한: 공동 업무/일정/인수인계 제목1~100자, 짧은 본문400자 이내,
물품 payload2048바이트·거래 사유80자 이내다. 이 제한은 민감정보 유출을 완전히 막는 필터가 아니다.
짧은 문장에도 학생 이름/증상이 들어갈 수 있으므로 금지 안내·권한 제한·신고/정정 절차가 함께 필요하다.

Google/Supabase Auth가 공급자로부터 이메일·프로필을 수신할 수 있다는 사실과 Workspace 최소 수집을 구분한다.
Workspace에서는 UUID·학교 member code를 우선하고 이메일/실명을 추가 요청·복제하거나 재직 증거로 쓰지 않는다.
Managed Auth 자체의 공급자 수집·보존·고지 범위도 운영 개인정보 검토에 포함한다.

운영자 allowlist의 등록/회수는 승인된 배포 신원만 담당한다. 09D installer에서 해당 신원에
operators table의 필요한 SELECT/INSERT/UPDATE와 일치하는 RLS provisioning 정책을 명시적으로 부여해야 한다.
앱·학교관리자·ws_bootstrap_operator에는 operator 등록권을 주지 않는다. 현재 합성 fixture의 postgres seed는
실제 managed 환경에서 이 provisioning이 가능하다는 검증이 아니며 운영 적용 절차로 복사하지 않는다.

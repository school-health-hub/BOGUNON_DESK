4. RLS·GRANT 실행 확인
클라이언트는 LOGIN school_client -> SET ROLE authenticated 경로로 호출했다.
school_client는 runtime/owner/reader 역할의 member가 아니며 runtime으로 SET ROLE
할 수 없다. 미인증 시험은 별도 school_anon -> anon 경로를 사용했다.
공개 invoker -> 비노출 purpose definer -> 비소유 runtime -> RLS로 실제 실행됐다.
invoker와 원시 테이블 GRANT 부족을 postgres/service_role 실행으로 우회하지 않았다.
원시 SELECT/UPDATE, auth.sessions 읽기, 내부 actor helper 호출, audit UPDATE/DELETE,
runtime role 자체의 audit 수정·삭제도 거부됨을 확인했다.
Runtime RLS 방어층 시험에서는 학교 A claims로 학교 B SELECT가 0행, UPDATE도
0행이었다. 이 시험의 role 주입은 명시적인 로컬 방어층 probe이며 일반 RPC 성공
증거는 school_client로만 수집했다.

7. 발견·수정한 문제 및 남은 차이

통과만으로 처음 사용자의 계정 생성이 검증되지 않았음을 확인했다.
SELECT 정책이 생성 전 actor ID를 요구한 것이 원인. 본인 auth.uid와 live session을
기준으로 수정했다. pre_fix_results.json에 33PASS/1FAIL을 보존하고 빈 DB에서
migration과 전체 테스트를 재실행하여 최종 34PASS/0FAIL로 확인했다.

참여 epoch는 별도 membership_terms FK로 보존한다. 재가입시 새 term을 생성하고
이전 override를 현재 권한에 합치지 않는다. 과거 term/override 이력은 유지한다.
학교별 advisory transaction lock은 작은 학교의 정확성을 우선하는 직렬화 방식.
성능 최적화/대규모 학교 부하는 이번 검증 대상이 아니다.
